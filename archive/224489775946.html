CLEANROOM AI · AI 실전 18 챗봇 창을 따로 열던 시대는 끝났다 — 제미나이 'Gems → Skills' 전환과 @·/ 인라인 업무 조립 실전 2026년 11월 Gems 이관 대응부터 실제 보유 스킬 9종의 3계층 @ 멘션 조합·경계 점검까지

2026년 11월 기준, 지난 [AI 브리핑.10]에서는 메모장으로 SKILL.md를 직접 작성하는 원리를, [AI 브리핑.31]에서는 제미니의 '작업(Tasks)' 탭을 살펴보았습니다. 이번 [AI 실전 18]에서는 2026년 11월 17일부터 본격화된 구글 제미나이의 'Gems → Skills' 전환을 계기로, 필자가 실제 제미나이 입력창에 @를 눌러 불러 쓰는 9종의 실무 스킬과 3계층 인라인 조립 루틴을 해부합니다.

“문체�� 맞추는 챗봇, 글을 검수하는 챗봇, 발표 자료를 다듬는 챗봇을 각각 만들어 두었는데, 왜 매번 창을 바꿔 가며 결과물을 복사해서 옮겨야 할까?”

맞춤형 챗봇(Gem)을 목적별로 만들어 두고도 결국 창을 오가며 붙여넣기를 반복해야 하는 번거로움이 컸습니다. 이제는 전용 챗봇 창으로 이동하는 대신, 일반 대화창 안에서 @ 멘션 한 번으로 내가 등록한 여러 단위 스킬을 역할별로 겹쳐 호출(Stacking)하는 방식으로 작업 흐름을 재설계할 수 있습니다.

1. 무엇이 달라졌는가: '독립된 챗봇 창'에서 '대화창 안의 조립 블록'으로

구글은 2026년 11월 17일부터 개인 구글 계정(18세 이상, 활동 보관 설정 활성화 기준)을 대상으로 기존 맞춤형 챗봇인 Gems를 읽기 전용(Read-Only)으로 전환하고, Skills로 자동 변환하기 시작했습니다.

가장 큰 변화는 인터페이스 위치가 아닙니다. 기존 Gem이 매번 별도의 대화방으로 들어가 한 번에 하나의 페르소나만 실행하는 구조였다면, Skill은 일반 대화창이나 구글 워크스페이스(Gmail·Docs·Drive·Slides·Chat) 맥락 안에서 필요한 순간 바로 불러 쓰는 모듈형 지침 블록입니다.

더욱이 Skills는 오픈 표준인 마크다운(SKILL.md) 기반 구조를 따르므로, 특정 플랫폼 화면에 갇힌 설정값이 아니라 일반 텍스트 문서 형태로 관리하고 이식하기가 한결 수월해졌습니다.

이 구조 변화는 제약·바이오 품질관리(GMP) 현장에서 문서 체계를 설계하는 방식과 닮아 있습니다. 하나의 거대한 통합 표준작업지침서(SOP) 안에 검체 채취, 기기 세척, 데이터 기록 규칙을 모두 몰아넣는 대신, 변경과 검증이 쉬운 '단위 작업 표준(Unit Operation SOP)'으로 쪼개 필요한 공정마다 조립해 쓰는 원리입니다.

다만 비유의 한계는 분명히 짚고 넘어가야 합니다. 공식 GMP SOP는 QA의 변경관리와 승인 서명이 수반되는 규제 대상 문서이지만, 제미나이 Skills는 어디까지나 비규제 초안 정리와 문서 구조화를 돕는 개인·팀 단위 프롬프트 보조 도구입니다.

2. 실전 해부: 실제 등록한 스킬 9종을 '3개 계층'으로 나눈 기준

실제 한국어 제미나이 웹 화면(Hydrogen 모델)의 입력창에서 @를 입력하면, 상단 아바타 항목 바로 아래에 내가 등록해 둔 스킬 목록이 즉시 펼쳐집니다.

실제 목록을 보면 단순히 기능이 많은 것이 아니라, 지난 [AI 브리핑.17]에서 다룬 3계층 Skill Stack(맥락·제작·검증) 구조에 맞춰 역할이 분리되어 있음을 확인할 수 있습니다.

실제 보유 제미나이 스킬 9종의 3계층 역할 배치

1계층: 맥락·문체·준비user-instructions개인 기본 작업 맥락 및 맞춤형 지침 제공

3계층: 검수·감사·다각화get-more-perspectives결정을 내리기 전 3~5가지 관점을 파악해 시각 편향 방지

여기서 실제 화면에서 바로 배울 수 있는 실전 설계 포인트가 세 가지 드러납니다.

1. 생성 경로와 수동 이관 준비는 단순합니다.

기존 Gem을 옮길 때는 좌측 사이드바 Gems → Edit에서 지식 파일을 먼저 내려받고, Customize(맞춤 설정) → Skills → Create 경로로 들어가 제목·설명·지침을 등록합니다.

2. 한글-하이픈 명칭과 명시적 발동 조건도 그대로 작동합니다.

실제 목록의 영상-제작처럼 한글과 하이픈(-) 조합도 문제없이 등록·호출됩니다. 또한 영상-제작("영상 프롬프트 제작해줘! 라고 하면 스킬 발동")이나 split-screen-infographic("'인포그래픽'을 직접 언급하지 않아도 조건 충족 시 발동")처럼 언제 켜져야 하는지 트리거 조건을 설명란 첫머리에 적어 두면 자동 인식 정확도가 높아집니다.

3. '만드는 스킬'과 '따지는 스킬'을 분리해 두어야 합니다.

슬라이드를 짜는 ppt-slide-skill이나 초안을 다듬는 스킬 옆에, 냉정하게 결함을 찾는 cleanroom-writer-reviewer와 audit-skill을 별도로 분리해 두어야 자기 합리화 없는 교차 검증이 가능해집니다.

독자분들도 본인 계정에 바로 3계층 미니 스킬 세트를 만들어 테스트해 보실 수 있도록, 필자의 실제 스킬 내부 원문이 아니라 위 3가지 핵심 역할(문체·제작 / 검수 / 감사)을 본떠 독자 실습용으로 재구성한 참고용 미니 템플릿을 아래에 정리했습니다.

독자 참고용 미니 템플릿 ① my-writing-tone (1계층: 기본 문체·형식 고정 예시)
[역할] 모든 보고·공유 초안을 우리 팀의 표준 문체와 개조식 구조로 맞춘다. [규칙] 1. 문장은 2~3줄 단위로 간결하게 끊고, 과장된 형용사나 모호한 수식어를 배제한다. 2. 전문 약어가 처음 나오면 국문(영문 약어) 형태로 1회 병기한다. 3. 원문에 없는 수치나 사실은 임의로 추정해 채우지 말고 [확인 필요]로 남긴다.
독자 참고용 미니 템플릿 ② draft-fact-reviewer (3계층: 초안 논리·사실 검수 예시)
[역할] 작성된 초안에서 사실과 추정의 혼재, 내부 모순, 근거 없는 수치를 점검한다. [규칙] 1. 관찰 사실과 담당자 추정이 한 문장에 섞여 있으면 분리 수정을 제안한다. 2. 출처나 실측 근거가 없는 시간·비율 수치를 찾아 [근거 확인 필요] 태그를 붙인다. 3. 전체 글을 다시 쓰기 전에 발견된 결함 목록을 표(위치 | 문제 | 수정안)로 먼저 보고한다.
독자 참고용 미니 템플릿 ③ pre-audit-checker (3계층: 품질·절차 취약점 사전 점검 예시)
[역할] 업무 절차 초안이나 데이터 처리 흐름을 품질 감사(Audit) 관점에서 사전 점검한다. [규칙] 1. 누가, 언제, 어떤 원본 데이터로 검증하는지 책임자와 기록 남김(Audit Trail) 누락 여부를 확인한다. 2. 예외 상황(이탈·오류 발생 시 중단 기준)이 빠진 흐름은 보완 질문으로 뽑아낸다. 3. 최종 승인 판정은 사람이 내린다는 전제하에 '보완 권장 사항'만 구조화해 제시한다.
3. 실전 조합: @ 인라인 스태킹으로 끝내는 2가지 현장 시나리오

스킬 9종을 3계층으로 나누어 두면, 오늘 해야 할 일에 맞춰 필요한 스킬만 @로 골라 한 문장 안에 겹쳐 부를 수 있습니다. 대표적인 실전 조합 두 가지를 살펴보겠습니다.

조합 A. 콘텐츠 제작·검수·시각화 파이프라인

@match-my-writing-style + @cleanroom-writer-reviewer + @split-screen-infographic

평소 내가 쓰는 문체로 초안을 다듬고(match-my-writing-style), 적대적 검수 기준에 따라 사실·문체 결함을 걸러낸 뒤(cleanroom-writer-reviewer), 글의 핵심 대비 구조를 대표 이미지 프롬프트(split-screen-infographic)까지 한 흐름으로 뽑아내는 조합입니다.

조합 A 입력 프롬프트 예시 (재구성 — 비기밀 블로그·사내 칼럼 작성 시나리오)
@match-my-writing-style @cleanroom-writer-reviewer @split-screen-infographic 아래 메모는 이번 주 사내 뉴스레터에 실을 '회의록 구조화 팁' 초안이야. 먼저 내 평소 문체 기준을 반영해 다듬고, 근거 없는 수치나 과장 표현이 없는지 검토한 뒤, 글 상단에 들어갈 스플릿 스크린 대표 이미지 프롬프트까지 함께 정리해 줘. [초안 메모 붙여넣기]

조합 B. 제약·바이오 QC 실무 — 회의 준비·발표 설계·사전 감사 파이프라인

@prep-for-meetings + @ppt-slide-skill + @audit-skill (필요 시 @get-more-perspectives 추가)

지난 회의 기록과 할 일 메모를 모아 보고 골격을 세우고(prep-for-meetings), 제약·바이오 QC 문서 규격에 맞춰 발표 슬라이드 구성을 짠 뒤(ppt-slide-skill), GxP 실사 및 CSV 감사 시 지적될 만한 빈틈을 미리 짚어내는(audit-skill) 조합입니다.

조합 B 입력 프롬프트 예시 (재구성 — 비기밀 QC 시스템 점검 회의 준비 시나리오)
@prep-for-meetings @ppt-slide-skill @audit-skill 아래에 정리한 비식별 공정 데이터 검토 메모를 바탕으로 내일 오전 내부 공유용 발표 슬라이드 3장 구성을 제안해 줘. 그리고 발표 전 팀 내부적으로 먼저 확인해야 할 GxP·CSV 감사 관점의 취약점 체크리스트를 표로 정리해 줘. [비식별 회의 메모] "최근 실험실 간이 데이터 시트 백업 주기를 주 1회에서 일 1회로 변경하려 함. 파일 명명 규칙 통일안과 담당자 수동 확인 로그 서식 초안을 마련 중이며, 내일 회의에서 적용 범위와 검증 절차를 논의할 예정."

위 조합 B처럼 '만드는 스킬(ppt-slide-skill)'과 '감사하는 스킬(audit-skill)'을 한 프롬프트에서 겹쳐 호출하면, 다음과 같은 구조화된 결과를 얻을 수 있습니다. (아래 표는 독자의 이해를 돕기 위해 가상 비기밀 시나리오를 바탕으로 재구성한 산출물 예시입니다.)

조합 B @ 인라인 스태킹 실행 산출물 예시 (재구성)

단계별 호출 스킬역할 분담 (계층)재구성 출력 핵심 내용
@prep-for-meetings1계층 (맥락·준비)회의 안건 3건 도출: ① 백업 주기 변경 배경, ② 파일 명명 규칙 통일안, ③ 수동 확인 로그 서식 및 미결 이슈
@ppt-slide-skill2계층 (발표 설계)3장 슬라이드 아웃라인 구성: Slide 1 변경 목적 및 현행 대비표, Slide 2 신규 백업·명명 흐름도, Slide 3 예외 처리 및 일정
@audit-skill3계층 (GxP·CSV 감사)사전 점검 질의 3건 제시: ① 백업 파일 무결성(원본 대조·해시/크기) 확인 방법 누락, ② 수동 로그 작성자·검토자(Second Person Review) 분리 여부, ③ 변경관리(Change Control) 등록 필요성 검토

이처럼 @ 하나로 서로 다른 계층의 스킬을 겹쳐 쓰면, 한 명의 AI에게 "글도 쓰고 감사도 하라"고 막연히 시킬 때보다 단계별 기준이 선명하게 분리됩니다.

4. 현업 도입 시 반드시 점검해야 할 3가지 경계

스킬을 잘 설계해 두었더라도, 실제 조직 업무에 적용하기 전에 기술적 제약과 보안 경계를 먼저 확인해야 합니다.

1. 개인 앱과 Google Workspace 스킬은 자동으로 동기화되지 않습니다.

구글 공식 지원 문서에 명시된 대로, 개인 Gemini 앱에서 만든 스킬과 회사 Workspace 앱(Docs·Gmail·Workspace Studio) 또는 Gemini Enterprise의 스킬은 서로 자동 연동되지 않습니다. 개인 계정에서 실험하고 검증한 스킬은 사내 승인 환경으로 별도 복사해 옮겨야 합니다.

2. 스킬을 많이 부를수록 계층 충돌을 점검해야 합니다.

실제 보유 목록처럼 9개 안팎의 스킬을 운영할 때, 같은 계층 안에서 상충하는 지침(예: "한 줄 요약하라" vs "모든 세부 근거를 나열하라")을 동시에 @로 호출하면 출력이 흔들립니다. 1계층(맥락) → 2계층(제작) → 3계층(검수·감사) 순으로 한 계층당 필요한 모듈만 골라 조합하는 습관이 중요합니다.

3. 사내 기밀 원문과 실제 식별 정보는 입력 전 반드시 비식별화합니다.

[쉬어가는 이야기 ②]에서 정리한 기준과 동일하게, 외부 클라우드 개인 계정 환경에 사내 미공개 제품명, 실제 배치·로트 번호, 환자·임직원 개인정보를 그대로 입력해서는 안 됩니다.

마치며

Gems에서 Skills로의 전환은 단순한 메뉴 이름 변경이 아니라, AI를 '미리 만들어진 별도 방에 들어가 대화하는 대상'에서 '내가 일하는 대화창 위로 역할별 규칙 블록을 @로 불러 조립하는 도구'로 바꾸는 변화입니다.

거창한 자동화 시스템을 한 번에 구축하려 하기보다, 오늘 본인이 가장 자주 쓰는 문체·맥락 규칙 하나와 검수·감사 기준 하나만 분리해 등록한 뒤 대화창에서 @로 나란히 불러 보시기 바랍니다. 만드는 역할과 따지는 역할 두 개만 분리되어도 결과물의 안정감이 눈에 띄게 달라집니다.

자주 묻는 질문

Q1. 기존에 만들어 둔 Gem이 사라지면 작업 내용도 다 날아가나요?

아니요, 개인 계정의 기존 Gem은 읽기 전용으로 바뀐 뒤 자동으로 초안 스킬(Draft Skill) 형태로 변환되며 기존 대화 기록도 유지됩니다. 다만 안전을 위해 중요한 지식 파일은 Gem 편집 화면에서 미리 PC로 내려받아 두는 것을 권장합니다.

Q2. 회사에서 쓰는 Google Workspace 계정에서도 바로 Gems가 없어지나요?

아니요, Google Workspace 비즈니스·엔터프라이즈 계정의 Gems는 최소 2027년 3월 1일 이후, 교육용 계정은 2027년 6월 1일 이후에 전환될 예정입니다. 다만 Workspace Studio에서 기존 Gem 기반의 새 자동화 플로우 생성은 중단되었으므로 신규 작업은 Skills 기준으로 설계하는 편이 좋습니다.

Q3. 한국어 제미나이에서 @ 입력만으로 스킬 목록이 바로 뜨나요?

네, 필자의 실제 한국어 제미나이 화면(Hydrogen 모델)에서도 입력창에 @를 입력하면 상단 아바타 메뉴 아래에 등록된 스킬 목록이 즉시 펼쳐지며, 영문과 한글-하이픈 명칭 모두 호출할 수 있습니다. 다만 개인 계정의 활동 보관(Keep Activity) 설정 여부와 순차 배포 일정에 따라 @ 및 / 호출 노출 시점은 계정마다 다를 수 있습니다.

AI 실전 18 · TAKEAWAY 하나의 거대한 프롬프트보다, 역할 계층이 나뉜 작은 스킬을 @로 조립하는 습관이 현장에 강합니다. 내가 만든 맥락·문체(1계층), 제작·시각화(2계층), 검수·감사(3계층) 스킬을 대화창에서 @로 겹쳐 호출하며 만드는 작업과 검증하는 작업을 분리해 보세요.
