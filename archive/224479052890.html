CLEANROOM AI · AI BRIEFING AI BRIEFING.24 (AI 브리핑) "MMLU 90점의 에이전트는 왜 내 엑셀 하나 못 고칠까? : 정적 벤치마크의 한계와 동적 실행 기반 평가(Agentic Evals)" AGENTIC EVALS 50% · METHOD VALIDATION (ICH Q2) 50% Why static multiple-choice benchmarks fail to predict real-world agent reliability, and how dynamic Agentic Evals align with pharmaceutical Analytical Method Validation (ICH Q2).
“모의고사 성적표가 현장의 직무 수행 능력을 보증하지 않듯, 단답형 벤치마크 점수가 에이전트의 실무 신뢰성을 대신해 주지는 않는다.”

새로운 AI 모델이 발표될 때마다 언론과 기술 리포트에는 화려한 벤치마크 점수표가 빠짐없이 등장합니다. 대학원 수준의 과학 지식 평가(GPQA), 종합 지식 평가(MMLU), 기초 코딩 평가(HumanEval) 등에서 최상위 모델들의 점수는 이미 80~90점대를 넘어 포화 상태에 다다랐습니다.

그런데 막상 이 모델을 업무용 에이전트로 연결해 실제 일을 시켜보면 당혹스러운 경험을 하게 됩니다. 사내 양식이 조금 바뀐 엑셀 파일 하나를 처리하다 멈추거나, 5단계 도구 호출 중 3번째 단계에서 파일 경로를 잘못 읽어 엉뚱한 결과물을 제출하는 것입니다.

왜 벤치마크에서는 90점을 받는 모델이 실무 현장에서는 사소한 예외 하나를 넘기지 못할까요? 그 이유는 기존 평가 방식이 '닫힌 시험지 위의 단답형 암기'를 측정해 왔을 뿐, '변동성이 있는 환경에서의 실행 안정성'을 검증하지 못했기 때문입니다. 지금 AI 엔지니어링의 표준이 정적 벤치마크에서 동적 실행 기반 평가(Agentic Evals)로 재편되고 있는 배경입니다.

1. 정적 벤치마크의 맹점: 오염(Contamination)과 단발성 채점

전통적인 LLM 벤치마크가 실무 능력을 예측하지 못하는 원인은 크게 세 가지 구조적 한계에서 비롯됩니다.

1. 데이터 오염(Data Contamination)과 암기:

공개된 벤치마크 문제들이 인터넷에 널리 퍼지면서, 차세대 모델의 사전 학습 데이터에 시험 문제와 정답이 이미 포함되어 버리는 현상이 빈번해졌습니다. 문제를 추론해 푼 것인지, 기출문제를 통째로 외워서 답한 것인지 구분하기 어려워진 것입니다.

2. 환경 피드백의 부재:

단답형 질의응답(QA)은 질문을 한 번 던지고 텍스트 한 덩어리를 받아 채점합니다. 반면 실제 에이전트 업무는 파일을 열고, 에러 메시지를 읽고, 도구를 다시 호출해 상태를 수정하는 다단계 상호작용(Multi-turn Interaction)입니다. 한 번의 실수를 스스로 복구하는 능력은 정적 시험지로는 결코 측정할 수 없습니다.

3. '결과 텍스트'와 '실제 상태 변화'의 괴리:

에이전트가 "요청하신 표를 수정하고 저장했습니다"라고 완벽한 한국어로 보고하더라도, 실제 파일 시스템을 열어보면 서식이 깨져 있거나 엉뚱한 시트에 덮어쓰기가 되어 있는 경우가 많습니다.

이러한 한계를 극복하기 위해 최근 커뮤니티와 연구계에서는 SWE-bench(실제 오픈소스 이슈 해결 및 테스트 통과 여부 검증), GAIA(웹 탐색·파일 처리·다단계 추론 기반 실무 과제)처럼 에이전트를 가상 환경(Sandbox)에 직접 풀어놓고 최종 산출물과 시스템 상태 변화를 채점하는 동적 실행 평가(Agentic Evals)로 중심축이 이동했습니다. 다만 최근에는 이러한 공개 동적 벤치마크조차 모델들이 해당 환경과 문제 패턴에 과적합(Overfitting)되면서, 사내 고유의 레거시 문서나 비공개 도구를 마주하면 다시 정답률이 크게 떨어지는 현상이 나타납니다. 결국 범용 성적표를 넘어, 우리 조직의 실제 업무 환경에 맞춘 자체 검증 체계가 필수적입니다.

2. 확률적 에이전트의 함정: pass@k가 아니라 pass^k를 보라

에이전트 평가(Agentic Evals)에서 가장 주목해야 할 통계적 개념은 pass@k와 pass^k의 차이입니다.

• pass@k (가능성 지표): k번 시도해서 단 한 번이라도 성공하면 합격으로 치는 지표입니다. 코딩 어시스턴트가 후보 코드 5개를 제안했을 때 그중 1개만 돌아가도 개발자가 골라 쓸 수 있는 환경에서는 유용합니다.

• pass^k (신뢰성 지표): k번 연속으로 실행했을 때 모든 시도가 빠짐없이 성공해야 합격으로 치는 지표입니다.

* 아래 계산은 단일 성공률의 체감 착시를 설명하기 위한 산술적 예시입니다.

만약 어떤 에이전트가 단일 작업에서 80%(0.8)의 성공률을 보인다고 가정해 봅시다. 겉보기엔 꽤 쓸 만한 수준처럼 보입니다. 하지만 이 에이전트가 실무에서 5번 연속으로 오류 없이 작동할 확률(pass^5)을 계산하면 0.8^5 ≈ 32.8%로 급락합니다. 10번에 7번꼴로 중간 어딘가에서 미끄러지는 시스템은 자동화 파이프라인에 올릴 수 없습니다. 동적 에이전트 평가는 바로 이 '운 좋게 한 번 맞춘 결과'를 걷어내고, 반복 실행 시의 분산과 일관성을 측정하는 데 초점을 맞춥니다.

3. 시험법 밸리데이션(ICH Q2)의 잣대로 본 에이전트 평가

제약·바이오 품질관리(QC)에서는 새로운 분석 기법이나 시험법을 현장에 도입하기 전, 반드시 시험법 밸리데이션(Analytical Method Validation, ICH Q2)이라는 엄격한 검증 절차를 거칩니다. "이 시험법이 의약품의 품질을 판정하는 데 사용할 수 있을 만큼 과학적으로 타당한가"를 입증하는 과정입니다.

Agentic Evals가 구축하려는 평가 프레임워크는 바로 이 시험법 밸리데이션의 핵심 기준들과 놀라울 정도로 닮아 있습니다.

ICH Q2 밸리데이션 항목제약 분석 시험에서의 의미에이전트 평가(Agentic Eval)에서의 검증 기준
특이성 (Specificity)방해 물질(불순물·부형제)이 섞여 있어도 오직 측정 대상 성분만을 정확히 구별해 내는 능력노이즈 문서, 불필요한 이메일 맥락, 프롬프트 인젝션(방해 신호)이 섞여 있어도 핵심 과업만 정확히 수행하며, 불필요한 파일 수정·미승인 도구 호출 같은 부작용(Side-effect) 없이 지정된 궤적(Trajectory) 내에서만 작동하는가?
정확성 (Accuracy)측정값이 참값(표준품의 실제 함량)과 얼마나 일치하는가에이전트가 도출한 수치, 수정된 파일, DB 변경 내역이 실제 정답 상태(Ground Truth)와 일치하는가?
정밀성 / 반복성 (Precision)같은 시료를 여러 번 반복 분석했을 때 결과값들이 서로 얼마나 흩어지지 않고 모이는가동일한 입력과 환경을 5~10회 반복 실행했을 때 pass^k 일관성이 유지되는가?
완건성 (Robustness)pH나 온도 같은 시험 조건이 미세하게 변해도 분석 결과가 무너지지 않고 버티는 힘사용자의 말투가 조금 바뀌거나, 입력 파일의 열 순서가 약간 달라지거나, API 응답이 지연되어도 절차가 붕괴되지 않는가?

특히 주목해야 할 축은 특이성 기반의 과정 검증과 완건성(Robustness)입니다.

최신 에이전트 거버넌스에서는 목표 달성 여부뿐만 아니라, 목표 달성 과정에서 불필요한 파일을 건드리거나 허용되지 않은 도구를 호출하는 부작용(Side-effect) 없이 지정된 궤적(Trajectory) 내에서만 작동했는지를 함께 검증합니다. 또한 정적 벤치마크에서 높은 점수를 받은 모델도 입력 표의 헤더 이름 하나가 Date에서 일자로 바뀌거나 빈 행이 하나 추가되면 루프에 빠지는 경우가 많으므로, 진정한 에이전트 평가는 깨끗한 정상 데이터(Happy Path)뿐만 아니라 의도적으로 조건을 흔든 변형 데이터(Perturbed Inputs)를 통과해야 비로소 실무 투입 자격을 얻습니다.

4. 비유의 한계: 절대 표준품의 부재와 '심판 모델'의 편향

시험법 밸리데이션의 프레임워크를 AI 평가에 적용할 때 반드시 경계해야 할 차이점도 존재합니다.

• 물리적 표준품 vs 주관적 채점 기준:

제약 분석에는 질량과 순도가 보증된 표준품(Reference Standard)이 존재하지만, 보고서 요약이나 고객 응대 같은 비정형 AI 과업에는 유일한 물리적 정답이 없습니다. 이 때문에 최근에는 또 다른 AI 모델이 채점관 역할을 하는 LLM-as-a-Judge 방식을 많이 쓰지만, 심판 모델 역시 "길고 공손한 답변을 실제 정확도보다 높게 평가하는 편향(Verbosity Bias)"을 가질 수 있습니다.

• 일회성 인증 vs 지속적 회귀 테스트:

분석 시험법은 한 번 밸리데이션을 마치면 기기와 시약 규격을 유지하는 한 오랫동안 유효합니다. 반면 에이전트는 기반 모델 업데이트, MCP 도구 스펙 변경, 사내 문서 포맷 변화에 따라 언제든 성능이 퇴보할 수 있습니다. 따라서 에이전트 평가는 한 번 통과하고 서랍에 넣는 인증서가 아니라, 코드 변경 시마다 자동으로 돌아가는 CI/CD 회귀 테스트(Regression Gate)로 상시 운영되어야 합니다.

5. 실무 적용: 우리 팀의 에이전트 '릴리스 게이트'를 만드는 4단계

거창한 오픈소스 벤치마크를 전부 구축하지 않더라도, 사내 실무에 AI 에이전트나 자동화 워크플로우를 도입할 때 아래 4단계의 미니 밸리데이션을 거치면 시행착오를 크게 줄일 수 있습니다.

1. '이상적 질문' 대신 '현장의 지저분한 실제 케이스' 15~20건을 수집하십시오. 프롬프트를 만들 때 잘 돌아갔던 예시 2~3개로 테스트하지 마십시오. 실제로 현업에서 날아오는 오탈자 섞인 문서, 병합된 셀이 있는 엑셀, 예외 조건이 겹친 과거 실패 사례를 모아 골든 테스트 세트(Golden Dataset)를 만드십시오. 2. 채점 기준을 '문장의 유창함'에서 '결정론적 체크리스트'로 쪼개십시오. "답변이 좋은가(1~5점)" 같은 모호한 평가 대신, [필수 수치 3개가 원문과 일치하는가? Y/N], [지정된 JSON/표 컬럼을 깨뜨리지 않았는가? Y/N], [근거 없는 추측을 하지 않았는가? Y/N]처럼 이분법적 통과 기준(Assertion)으로 분해하십시오. 3. 동일 테스트를 최소 3~5회 반복 실행해 반복성(pass^k)을 확인하십시오. 딱 한 번 성공한 결과를 보고 실무에 배포하지 마십시오. 같은 입력으로 연속 실행했을 때 한 번이라도 규격을 벗어나는 변동성이 보인다면, 온도(Temperature) 하향이나 검증 스크립트 추가 등 구조를 먼저 보강해야 합니다. 4. 프롬프트나 모델을 바꿀 때마다 전체 테스트를 다시 돌리십시오. "프롬프트 한 줄만 고쳤으니 괜찮겠지"라는 방심이 실무에서 가장 잦은 회귀 오류(Regression)를 만듭니다. 수정 전후로 골든 테스트 세트의 통과율이 유지되거나 상승했음을 확인한 뒤 배포하는 습관이 곧 엔지니어링의 시작입니다.

결론: 신뢰는 '최고 점수'가 아니라 '최저 변동성'에서 나온다

AI 시대의 초기에는 모델이 얼마나 놀라운 답을 한 번 내놓을 수 있는가(Peak Performance)에 열광했습니다. 하지만 에이전트가 실제 비즈니스의 톱니바퀴 안으로 들어오면서, 실무 현장이 요구하는 가치는 '가끔 천재적인 답'이 아니라 '언제 실행해도 흔들리지 않는 일관성(Reliability)'으로 바뀌고 있습니다.

외부에서 발표한 90점짜리 성적표는 모델의 잠재력을 보여줄 뿐, 우리 회사의 업무 규격에 맞는다는 보증서가 아닙니다. 우리 조직만의 데이터와 조건으로 완건성과 반복성을 검증하는 동적 평가 체계(Agentic Evals)를 갖추는 것, 그것이 "데모에서는 멋졌는데 실무에서는 못 쓰겠다"는 AI 도입의 흔한 좌절을 끝내는 가장 확실한 방법입니다.

💬 CleanRoom AI 인사이트 외부 벤치마크의 최고 점수가 우리 실무 환경의 안정성을 대신 증명해 주지 않습니다. 특이성·반복성(pass^k)·완건성을 점검하는 자체 동적 평가 게이트가 에이전트를 실무에 세우는 최소한의 밸리데이션입니다.
